6. H1 — FILE SECURITY
============================================================

Guest uploads are untrusted.

Apply the same or stronger protections already used by
MediaUploadService.

Required:

- JPEG
- PNG
- WEBP

Reject:

- SVG
- executable files
- HTML
- JavaScript
- arbitrary MIME types
- unsupported extensions

Validate actual binary/magic bytes.

DO NOT trust:

- Content-Type
- filename
- extension alone

Maximum size:

5 MB

Reject oversized files.

Generate a server-controlled unique filename.

Never use the customer-provided filename as the actual stored filename.

Prevent:

- path traversal
- ../
- absolute paths
- arbitrary directories
- filename injection

Store under a dedicated controlled location, for example:

uploads/custom-cake-references/

Use the project's existing configured storage root.

Do NOT hardcode an absolute production filesystem path.

14. H2 — AUTHORITATIVE CAPACITY CALCULATION
============================================================

For a selected:

shop
+
delivery date
+
delivery slot

calculate the number of capacity-consuming orders.

Conceptually:

capacity = shop_delivery_slots.max_orders

booked =
COUNT(capacity-consuming orders
      for same shop
      for same delivery date
      for same delivery slot)

remaining = capacity - booked

If:

remaining <= 0

the slot is unavailable.

DO NOT calculate capacity only on the frontend.

DO NOT use a frontend counter.

DO NOT store a duplicated counter unless inspection proves it is
necessary and safe.

Prefer deriving the count from authoritative order records.

============================================================
15. H2 — IMPORTANT: CONCURRENCY / OVERBOOKING
============================================================

This is mandatory.

Do NOT implement:

COUNT orders
then
INSERT order

without concurrency protection.

Race example:

Capacity = 5
Booked = 4

Customer A checks → 1 available
Customer B checks → 1 available

Both submit simultaneously.

The result must NOT be:

6 orders.

Only one should successfully consume the final capacity.

Inspect the existing database and transaction architecture.

Choose an appropriate PostgreSQL/JPA strategy such as:

- row-level locking
- pessimistic locking
- atomic conditional update
- another database-backed concurrency-safe approach

Choose the strategy that fits the existing project.

Do NOT use:

- Java synchronized
- in-memory counters
- frontend locking
- client-side disabling

Capacity enforcement must survive multiple backend instances.
